**THE DIRECTIVE (Chase, 2026-07-22):** always differentiate OTTO-TWIN's purpose (world simulator / data generator) from OTTO-Q's (orchestration brain). Never let a twin build bleed into OTTO-Q or vice versa. The end state: **real autonomous-vehicle data and telemetry plug directly into OTTO-Q** — "when we are ready for production, we simply send real telemetry communication to OTTO-Q instead of the simulation data." He expects REST API / webhook style ingestion (mentioned V2G as a guess) and wants a clean plug-in for OEM AV data at demo/production time.

**Why:** the whole pitch is that OTTO-Q orchestrates ANY fleet's returns/servicing/energy. If sim-specific logic leaks into the brain, the production cutover becomes a rewrite instead of a feed swap.

**How to apply (build rules):**
- **The seam = the data tables + command bus, not the generators.** OTTO-Q reads `ottoq_telemetry_packets`, `ottoq_vehicle_dispatches`, wear/needs state, and emits via `ottoq_vehicle_commands` + `ottoq_comms_messages`. Twin functions (`ottoq_sim_*`) are WRITERS into that seam. Real ingestion must be a parallel writer into the SAME tables/shapes — never a new consumer path in the brain.
- **Naming discipline:** anything `ottoq_sim_*` = twin-side (replaceable at production); decision fns (decide_tick, shield, book_appointment, evaluate_return_need, orchestrate, planners) = brain-side and must never read sim-only artifacts directly (cards/profiles are twin world-state; the brain reads their EFFECTS via telemetry/wear/needs).
- `data_source`/`ingest_source` columns already tag provenance ('twin' vs 'production'/'oem') — keep stamping them; that's the audit line between sim and real.
- **Real-world protocols (plain-language map for Chase):** OEM AV telemetry arrives via the OEM's fleet API — push webhooks (REST POST of JSON: position, SoC, health codes, ETA) or polling their API; that lands in an ingest endpoint (Supabase edge function) that writes telemetry packets + triggers the same return/booking handshake. **V2G / ISO 15118 is the charger-cable protocol** (vehicle↔charger energy negotiation) — that side is already modeled via OCPP (charger↔OTTO-Q); it is NOT the telemetry path. Pillar 2 already models MQTT / J2735 / ISO 20078 comms shapes.
- Existing brain-side contract work: SI-5 getState/decide/command API contract (task #104, done); Pillar 2 comms bus; `ottoq_sim_emit_arrival_webhook` shows the arrival-webhook shape the sim mimics.
- **PRODUCTION CUTOVER CHECKLIST (target):** (1) OEM webhook → `ottoq-ingest-telemetry` edge fn → telemetry packets + dispatch state; (2) return-intent webhook → `ottoq_book_appointment` (same handshake); (3) commands OUT via the comms bus → OEM dispatch API adapter; (4) chargers real via OCPP (already the modeled protocol); (5) turn OFF the twin's writers for that depot. Brain untouched.
