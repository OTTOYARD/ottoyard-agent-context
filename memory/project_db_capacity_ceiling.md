**Measured 2026-07-30 on `gxdrcyphqjzjsuhxuqtg` (otto-q-core):**
- database **11 GB**, of which `public.ottoq_events` is **9.1 GB** (~83%). Heap ≈8.3 GB, indexes ≈750 MB. Earlier in the day it was 7.6 GB — it grows every run.
- Symptom set: checkpoints writing **4 buffers in 12 seconds** (absurd — that is disk throttling, not load), catalog queries taking 24-100 s, `pg_cron` "job startup timeout" on every job, intermittent `could not accept SSL connection`, and the SQL connector dying for minutes at a time while the project reports `ACTIVE_HEALTHY`.
- **Nothing was running** during the worst of it (`pg_stat_activity` empty, no sim run, cert queue drained 38/38). So this is NOT query load — it is a small instance's burst-credit disk being unable to serve a 9 GB table against a ~224 MB cache.
- **PostgREST is wedged on `PGRST002`** ("could not query the database for the schema cache") — it cannot complete catalog introspection on the throttled disk, so it 503s every REST call and retries forever. `NOTIFY pgrst, 'reload schema'` did NOT clear it. Direct SQL works intermittently in the same window; **the two paths fail independently, so always check both before concluding "the DB is down."** This blocks the cockpit and every edge function, not just my tooling.

**Two contributors found and FIXED (2026-07-30):**
1. `pg_stat_statements` had filled to its **5,000-entry ceiling**, and Supabase's own platform telemetry queries scan it constantly — those scans were taking **10-33 s each and timing out**, burning CPU/IO in a loop. `extensions.pg_stat_statements_reset()` took it to 3 entries. (Track is back to `top`; `auto_explain.log_min_duration` is 10 s, which is why slow-query plans show in the logs.)
2. **8 of 18 indexes on `ottoq_events` had NEVER been scanned** (`idx_scan=0` while siblings showed 1M+, so counters were live) — yet each was an extra write on EVERY event insert, the write amplification behind 7-22 s ticks (see [[project_tick_cost_root_cause]]). Dropped, 18→10, definitions snapshotted under label `pre_drop_unused_event_indexes_2026_07_30` in `ottoq_schema_snapshots` (recreate to undo).

**NOT fixed — needs Chase's decision, because both options cost something:**
- **Purge/partition the event log.** Deleting rows is destructive to the black-box forensic record, and a plain DELETE makes things WORSE short-term (heavy WAL on a throttled disk) and does not return space to the OS without `VACUUM FULL` (needs double the space) or a partition drop. The clean long-term shape is **time/run partitioning** so old runs are dropped by detaching a partition, plus retention that matches his stated rule (keep only the previous completed run — see [[project_demo_loop_ops]]).
- **Upgrade compute/disk.** Costs money, fixes it immediately, no data loss. Given the deployment bar in [[project_deployment_bar]] and that every cert run writes GBs, this is probably the honest answer before the next big battery.

⚠️ **The re-cert battery will make this worse**: 3 seeds × 3 policies × 48 ticks writes a large volume of events into the same 9 GB table. Do not queue it until capacity is resolved, or it will re-wedge the box. Full resume protocol is in [[project_ottoq_twin_boundary]].

3. **🔴 PARTITIONING COSTS THE FK GRAPH — hard Postgres rule, no workaround.** A partitioned table's PK/UNIQUE **must include the partition key** → PK becomes `(event_id, occurred_at)` → no unique constraint on `event_id` alone → **all 10+ inbound FKs referencing `ottoq_events(event_id)` must be dropped permanently** (rules_engine ×3, emergency_cascade ×2, audit_reports, counterfactuals, sla_scorecards, anomaly_detection, + self-FK `parent_event_id`), and `event_seq`'s **global UNIQUE is lost** (only `(event_seq, occurred_at)` is legal). Matters because this table's pitch is "audit-defensible, OEM-reviewable". **But I overstated it:** those FKs are `ON DELETE SET NULL` and the 48h purge already nulls them, so the guarantee is ALREADY bounded to the retention window; the real delta is honest-`NULL` → **dangling** ID, cheaply mitigated by a sweep.
4. **⭐ RUN-BASED PARTITIONING IS IMPOSSIBLE — and it's a live compliance bug.** `ottoq_record_event` takes `p_sim_run_id`/`p_data_source` but **DEFAULT NULL/'production'**, and the per-row state-change triggers (`ottoq_vehicles_state_change`, `_stalls_`, `_schedule_tasks_`, `20260514_layer1_event_journal.sql:684-847`) **never pass either**. So the highest-volume writer tags sim events `sim_run_id=NULL, data_source='production'` → LIST-by-run leaves the bulk undroppable, **and sim events pollute OEM compliance reports** (schema comment: "OEM compliance reports filter to production only"). Only `occurred_at` RANGE covers 100%.
5. **`occurred_at` is ALWAYS wall-clock, never sim time** — `ottoq_record_event` hardcodes `v_occurred_at := NOW()`, no `p_occurred_at` param, backed by `CHECK no_future_events`. Only 2 `INSERT INTO ottoq_events` sites exist repo-wide (both are record_event versions). So time partitioning is safe.
6. **⭐ THE GROWTH ENGINE (root cause of the 9 GB):** state-change triggers store **three copies of every row change** — `p_payload` (diff) + `previous_state` (full `to_jsonb(OLD)`) + `new_state` (full `to_jsonb(NEW)`) — ×116 vehicles × every tick, plus stalls/schedule_tasks. Fattest AND most numerous rows. **Chase APPROVED dropping `previous_state`** (rebuildable from diffs) bundled with the cleanup. Likely also the biggest lever on the 7-22s tick.
7. **Two migration traps that would break everything, found by reading not running:** (a) `event_seq BIGSERIAL`'s sequence is **OWNED BY** the old column — `DROP TABLE` old kills it and every subsequent insert fails; must `ALTER SEQUENCE ... OWNED BY NONE` first, re-own after. (b) **Views bind by OID, not name** — after `RENAME`, all ~8 dependent views silently still read the LEGACY table; must `CREATE OR REPLACE VIEW` each. Also `LIKE ... INCLUDING INDEXES` **fails** on a partitioned table (tries to recreate PK on non-partition-key); and LIKE copies **no** RLS policies, grants, or triggers.
8. **⭐ SEQUENCING VERDICT (why the "one shot or double rewrite" pressure is fake):** reclaim (swap + `DROP`, non-partitioned) + growth fix + 1-week retention are all certain wins needing no partitioning decision. The double-rewrite argument only holds *while the table is 9 GB* — once small, converting to partitioned later is cheap. So **defer partitioning, decide on measured growth.**
9. **Chase's retention rule CHANGED** (supersedes "keep only the previous run"): **keep ~1 week / "the last handful" of runs**, because the code changes constantly so older runs aren't comparable. Wants the black box organized: immediate stop→download of the run that just ended + rolling 1-week backlog. Standing authorization to delete older data — but still show the cutoff + counts before an irreversible delete.

**🔐 2026-07-30 (NINTH pass) — EVENT SIGNING NOW WORKS FOR THE FIRST TIME. And I opened + closed a live secret leak doing it.**
- **ROOT CAUSE was `secret_ref = 'env:OTTOQ_SIGNING_KEY_SYSTEM_V1'`** — the secret was expected in an **edge-function environment variable**, and `ottoq_resolve_signing_secret` read **only session GUCs**. Events are written by **pg_cron** (metronome / depot tick), which has no env and sets no GUC ⇒ unsigned **by construction**, silently, since 2026-05-14. `ottoq_signing_keys` stores a **`secret_ref` pointer, NOT a secret**, so "just read the key from the table" was never possible.
- **FIX (migration `resolve_signing_secret_from_vault`):** provisioned a 256-bit key via `vault.create_secret` as **`ottoq_signing_key_system_v1`** (supabase_vault 0.3.1 was installed but unused; value never displayed), repointed `secret_ref` → `vault:ottoq_signing_key_system_v1`, and added a **3rd resolution step**: GUC → default GUC → `ottoq_signing_keys.secret_ref` `vault:<name>` → `vault.decrypted_secrets`. GUC stays FIRST so the edge-function path is unchanged (purely additive). Vault read is wrapped in an exception block — recording must never fail because signing failed.
- **⭐ HOT-PATH SAFE, with a receipt (RULE 0 timing):** cold Vault decrypt **3.36 ms** (once per session), then cached into the session GUC ⇒ **warm resolve 0.0088 ms/call**, **full `ottoq_sign_event` 0.0272 ms/call** (n=2000). Against a 28 ms `ottoq_record_event` that is **~0.1% overhead**. Without the cache every event would pay 3.36 ms = a ~12% regression, so **the caching is load-bearing, not an optimisation.**
- **VERIFIED END-TO-END** (rolled back): real vehicle UPDATE → event `signed=t`, `len=64` (256-bit hex), `key=system:v1`, `ottoq_verify_event_signature` → **`valid=t`**, and a scoped audit report returned **`complete`, signed 1/1** — the first genuine "complete" the audit chain has ever produced.

**🔴 2026-07-30 (third pass) — 9-AGENT ADVERSARIAL VERIFICATION of the partition plan. ~40 findings, 11 outage / 9 data_loss. See §10 of `OTTOQ_EVENTS_PARTITION_PLAN_2026-07-30.md`. The plan was NOT safe as written and several of my own claims were WRONG:**

- **⭐⭐ DROPPING THE 8.3 GB WILL NOT LIFT THE I/O THROTTLE.** IOPS are provisioned independently of bytes used (gp3) or scale with *provisioned* volume size (gp2) — not used bytes. The real wins are working-set/cache-hit + O(1) retention. Never promise "this unwedges the box."
- **⭐⭐ PARTITIONING MAKES `PGRST002` WORSE.** Every partition is a new relation PostgREST must introspect — the exact op already timing out (~15 partitions now, ~200/yr). AND `CREATE TABLE … PARTITION OF` copies **neither RLS nor grants**, and Supabase's `ALTER DEFAULT PRIVILEGES … GRANT ALL … TO anon, authenticated` means **every nightly partition is a fully-exposed RLS-off table granting ALL to `anon` — forever, created by cron.** **MANDATORY FIX (solves all three at once): create partitions in a non-exposed schema** (`CREATE SCHEMA ottoq_parts; REVOKE ALL … FROM PUBLIC, anon, authenticated;`) — a partition may live in a different schema from its parent; the parent stays in `public` with its RLS.
- **⭐ MY "FKs are impossible, no workaround" WAS REFUTED.** FKs *can* reference a partitioned table since **PG 12**. Real workaround = **identity registry**: `ottoq_event_ids(event_id PK, event_seq BIGINT UNIQUE, occurred_at)` filled by an AFTER INSERT row trigger (clones to every partition); repoint all FKs there, keep `ON DELETE SET NULL`. Retention = DROP PARTITION for payload **+ a narrow DELETE from the registry — which is DML, so SET NULL still fires.** Preserves DB-enforced global uniqueness of event_id AND event_seq, and restores the event_seq INDEX (the cockpit feed orders by it). Cost: +1 heap +2 btree inserts on a 28 ms write path. **⭐ Deeper point for Chase: a DB-enforced reference to a row you've decided to delete is arithmetically impossible — the FKs were ALREADY doomed by the retention POLICY, not by partitioning; today they only "work" because SET NULL quietly erases the link. Partitioning changes NULL→dangling. That's the whole delta — I overstated it twice.**
- **⭐ `SET LOCAL` AS ITS OWN STATEMENT IS A NO-OP** (dies with its own implicit txn in autocommit) ⇒ **every timeout guard in the plan was silently absent.** Use plain `SET` on a **direct 5432** connection (never the pooler — `SET` and per-window transactions both depend on it) and `SHOW` it back.
- **⭐ RULE -1(a) IS INVERTED FOR TABLES.** That rule is about *functions* (default EXECUTE → PUBLIC). Supabase grants **table** privileges **directly to `anon`/`authenticated` by name**, so `REVOKE … FROM PUBLIC` alone leaves them holding INSERT/UPDATE/DELETE. Must be `REVOKE … FROM PUBLIC, anon, authenticated;` + verify via `aclexplode(relacl)`.
- **NO `DEFAULT` PARTITION** — it's a one-way trap: while it exists, adding ANY partition takes ACCESS EXCLUSIVE on it **and scans it, empty or not**; it also disqualifies `DETACH … CONCURRENTLY` and can never be pruned. Pre-create ~30 days ahead, alarm if tomorrow's missing.
- **BRIN/append-only correlation was REFUTED as an assumption** — defeated by `NOW()`-at-txn-start jitter over 7-22 s ticks, **FSM reuse from the DELETE retention already running** (fresh rows scattered into old holes), and unsummarised tail ranges. - **⭐ THE CHEAPEST PATH READS ZERO ROWS:** create the partitioned table, swap it in, **don't backfill** — serve the retained week from a view that `UNION ALL`s new + legacy, then DROP legacy once the week ages out. Copy I/O = 0, TOAST rewrite = 0, WAL = 0. Sidesteps the ordering defect, the TOAST rewrite (**which dominates cost, fully WAL-logged since Supabase runs `wal_level=logical`**), and the index-build timing problem.
