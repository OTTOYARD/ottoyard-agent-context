**Pillar 2 built 2026-06-27 (migration `oq_pillar2_comms_lines` on otto-q-core `gxdrcyphqjzjsuhxuqtg`).** Chase mandate: make the comms lines as close to the ACTUAL vehicle/OEM communication protocols as possible (both directions: vehicle→telemetry→OTTO-Q, and OTTO-Q→vehicle), for OEM/investor accuracy — "not just a toy simulation." Emulated in the twin now (broker-ready schemas); real MQTT broker integration deferred until real vehicles/team exist.

**Standards it's built to (researched 2026-06-27):**
- **Transport = MQTT** (de-facto connected-vehicle protocol; pub/sub, persistent, buffers through dropouts). Topics: `fleet/{veh}/telemetry/bsm`, `/cmd`, `/cmd/ack`, `/assist/req`, `/assist/resp`. QoS 1 telemetry/ack, QoS 2 commands (exactly-once).
- **Telemetry payload = SAE J2735 BSM** Part-1 core (msgCnt, secMark, position lat/long/elev, speed_mps, heading, accelSet long/lat/vert/yaw, brakes, size) + **EV ext** (soc_pct, usable_kwh) + **AV ext** (autonomy_level 4, ads_engaged, mission_state).
- **Envelope = ISO 20078 (Extended Vehicle/ExVe)**: vehicle_uuid, message_type, message_uuid, correlation_id, message_version, timestamp_utc, schema tag. (ISO 20078 = HTTPS/REST + OAuth2/OIDC for request/response vehicle data.)
- **Teleop = SAE J3016 remote assistance + BSI PAS 1886 (monitor/assist/drive roles) + 5GAA "Indirect Control ToD"** — operator advises, vehicle executes (indirect control); latency is the key modeled constraint (+200ms on the gate).

**Teleop model (Chase's spec):** normal orchestration commands (dispatch/recall/assign) are AUTO-APPROVED (deterministic standard-parameter actions); only EDGE cases outside normal queuing params pass the remote-assistance gate — e.g. `stage_hold`/queue-disrupt-to-temporarily-stage, `incident_triage_ack`. There an AI remote-assistant returns a tight APPROVE/DENY (confirms vehicle movement); human escalation only on deny. First-line responder is deterministic now, with a seam to escalate to the real agent (`ottoq-ottocommand`).

**Functions/table:** `ottoq_comms_messages` (the bus log: direction, topic, msg_type, qos, header, payload, status, latency_ms, correlation_id) · `ottoq_comms_envelope` · `ottoq_comms_emit_telemetry` (uplink BSM; dropout via the `telemetry_dropout` variability knob) · `ottoq_comms_send_command` (downlink + ACK; edge_case→gate) · `ottoq_comms_teleop_review` (AI approve/deny).

**PROVEN round-trip:** uplink BSM telemetry (real 68% SoC, QoS1, delivered) → `recall` command (QoS2, auto-approved) → ack → `stage_hold` edge command → assist_request (pending) → AI **approve** (200ms) → ack. Both directions, to spec.

**LIVE-WIRING ✅ DONE 2026-06-27 (migration `oq_pillar2_comms_live_wire`):** `ottoq_comms_advance(run, clock)` is a per-tick sweep over active/returning dispatches, wired INTO `ottoq_sim_advance_tick` (PERFORM call right after `advance_deployed_telemetry`, defensively wrapped so a comms error never breaks a tick). Each tick it: (a) emits a BSM uplink for every deployed vehicle (speed/heading plausible; position NULL until a real GPS feed — honest gap); (b) sends a `recall` downlink ONCE when a trip flips to `returning` (NOT EXISTS dedup vs the bus since dispatched_at); (c) when an `eta_delay` card is applied, fires a `stage_hold` through the teleop gate ONCE (edge case → assist_request → AI approve → ack). PROVEN end-to-end on a scoped test run (6 dispatches, 2 sweeps): 12 telemetry delivered (44–114ms), 2 recall+ack, 1 stage_hold + teleop approve(200ms) + ack; dedup held (commands once, telemetry continuous). Test scaffolding fully cleaned (run + all sim_run_id-scoped rows deleted; shared fleet never mutated — the mass-reassign was correctly blocked by the auto-mode classifier). **NOTE for testing runs:** `ottoq_sim_start_run(scenario, clock, scale, seed, run_by)` does NOT seed/claim a fleet (only inserts the run row); `auto_dispatch` deploys autonomous vehicles with `current_soc>=80` in states `staged_for_departure`/`offline`/`en_route_to_deployment`/`staged_awaiting_service(ready)`, capped by `ottoq_deploy_target_fraction(hour, ...)`. The depot fleet often carries stale state from prior runs.

**PLACEMENT DECISION ✅ (Chase, 2026-06-27) — the comms log lives in PULSE only; Orchestra reaches it through the AGENT, not a raw feed.** Chase's model: the raw communication layer is depot/teleoperator ground-truth → it belongs in **Pulse** (the depot/technician + teleoperator cockpit), where the people who ACT on it live. The **Orchestra** manager/asset-owner/OEM view stays clean — "they don't need to see the communication layer." Instead, when a manager notices something (e.g., a vehicle looks stuck), they **query the OTTOCommand agent** ("where is vehicle X in the queue? why is it stuck? what's its comms status?"); the agent reads the bus on the backend, returns it **line-by-line**, and can **escalate an action** (e.g., elevate this vehicle's queue position / re-stage it) to the depot/teleoperator side for approval. So the agent is the strategic-side *interface* to the comms layer — which is the more sophisticated, less-cluttered pattern, and it reuses what's already built (FC-4 `ottoq-ottocommand`).
